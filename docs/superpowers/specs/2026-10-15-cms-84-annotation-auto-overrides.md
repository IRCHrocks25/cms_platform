# CMS-84 — Preserve saved automatic text edits during annotation

When a raw template has renderer-generated `auto.n*` text slots, adding explicit `data-edit` markers can renumber the remaining automatic slots. Existing tenant or page overrides then appear on the wrong element or disappear. The CMS-72 render-preservation guard correctly rejects such a save. The owner's production banner specifically says "template defaults"; that comparison has empty content, so the owner's exact default-render change is a separate unresolved cause.

For an annotation save, identify old automatic text slots by their element path in the parsed HTML and map them to the same elements in the candidate. Move stored `auto.n*` values to the candidate's explicit stable field ID or new automatic ID, inside the same transaction as the template version. Preserve a content-version snapshot for each affected site/page. Compare the old render with the candidate render using migrated content before any write. If an old element is missing, its mapping is ambiguous, its new field is an incompatible type, or the destination has a different stored value, reject with the affected `auto.n*` ID. Retain the existing rendered-output guard for all other changes. No customer HTML or copy is included in tests or reports.

The migration applies only when the caller requests `preserve_rendered`, the annotation workflow's existing flag. Ordinary HTML editing and already stable fields keep their current behavior. Migration must cover both tenant home content and page content, preserve version history and atomic rollback, and avoid overwriting concurrent content edits by locking affected rows.
